This command is an isolated measurement adapter for campaign `historical-threefig-20261019`. It uses native StubEntry, StubFn, scheduler, cloud fallback, ProcessorManager, PAIX containers and finite idle TTL. It creates no edge function at startup and contains no desired-replica, load-triggered creation, or expiry policy.

Build and test on Linux in a source snapshot:

```
go test -race ./cmd/revision-threefig-dynamic
go build -o native-threefig ./cmd/revision-threefig-dynamic
```

On macOS, only `api.go` and `api_test.go` are selected, allowing network-free validation of JSON, payload, peer and destination contracts. `main_linux.go` and its native event/ownership tests require Linux and the repository's POSIX MQ/container dependencies. Passing portable tests does not establish Linux compilation or a successful runtime experiment.

Launch one process per owned host, using a new root for each independent repeat. Example argv (the external launcher supplies the host's actual address, frozen config, required MQ limits and rlimit):

```
./native-threefig --node=threefig-nj1 --kind=cloud --cpus=12 --address=IP1:31840 --http=0.0.0.0:31841 --root=/root/tmc-historical-threefig-20261019/run001 --config=/owned/calibrated-config.json
./native-threefig --node=threefig-nj2 --kind=origin --cpus=12 --address=IP2:31840 --http=0.0.0.0:31841 --root=/root/tmc-historical-threefig-20261019/run001 --config=/owned/calibrated-config.json
./native-threefig --node=threefig-nj3 --kind=edge --cpus=12 --address=IP3:31840 --http=0.0.0.0:31841 --root=/root/tmc-historical-threefig-20261019/run001 --config=/owned/calibrated-config.json
```

`--image` defaults to `docker.io/tide/threefig-20261019`; native code appends `:GOARCH`. The default commands are `["env","TIDE_DETECTIONS_PER_REQ=10","ORT_INTRA_THREADS=2","ORT_INTER_THREADS=1","python3","-u","/app/threefig_worker.py"]`. `--commands-json` changes the complete argv; every peer must use identical image/commands. This worker is the campaign layer around the existing actual YOLOX model and PAIX image. It returns an inference witness, which the collector must independently validate. The harness labels this `worker_witness_unverified`; HTTP/native success alone is not output validation.

`--config` loads ordinary native configuration; it must preserve `ttl_ms=2000`, `qos_ms=350`, and omit per-function QoS overrides. Node execution/network timing estimates and score weights remain native inputs. Without a config, native default timing estimates apply (430 ms execution), which can exclude every edge candidate under the 350 ms deadline; that is not evidence that autoscaling was attempted successfully. Record calibration and freeze suitable estimates before scored traffic. Configuration is read-only after startup.

The formal deployment budgets 12 logical application CPUs per host and the parent launcher assigns its 4 control CPUs separately on each 16-vCPU guest. The origin creates one entry reservation of 2 logical CPUs from its 12-CPU budget; the remaining 10 are eligible for native function creation when calibrated estimates/deadlines permit. The edge starts with no function. The cloud creates one native function reservation of 2 logical CPUs and two initial executors, matching the native cloud application builder's initialization. Native edge StubCreateEvent handlers choose their own executor initialization. Function reservations, borrowing and expiry are unmodified.

Startup, manifest and HTTP contract:

1. GET `/health` on each process returns a manifest item with `campaign,name,address,role,kind,cpus,stub,stub_mode,pid,image,commands`. Roles are strings. The execution edge correctly has empty `stub` and `stub_mode`. Gather those three exact health objects into one JSON array.
2. POST that array to `/peers` on all three nodes. Exactly one cloud, one persistent-entry origin and one initially cold execution edge is required. Each node accepts an even CPU budget from 2 through 12; the formal manifest uses 12/12/12, while the retained minimal Stage A manifest uses origin2/edge4/cloud4. Peer registration is one-shot; duplicate/malformed/mismatched manifests fail. No scored `/run` is accepted before the origin's peer registration.
3. GET `/state` on the origin for the complete view. `nodes` contains `node,role,total_cpus,remaining_cpus,reserved_cpus,updated_unix_ns,age_ms,valid`. These capacities come from native `NodeState.Capacity()`, updated by native ProcessorManager NodeSync heartbeats (5 ms nominal). `valid=false` means no usable heartbeat. Preserve freshness and observation age. The cloud excludes itself from native edge broadcasts, so its own local state endpoint can lack its own heartbeat; use the origin's observations.
4. `stubs` includes lifetime records and stop tombstones from read-only observation of normal native StubNew/StubSync/StubStop events: `stub_id,node,role,mode,status,created_unix_ns,stopped_unix_ns,updated_unix_ns,est_wait_ns`. Initial entry/cloud records are marked running at adapter construction; their timestamps reflect adapter observation, not a measured executor INIT event. Dynamic creation events follow native initialization/readiness. The observer does not alter event content or native handler delivery.
5. POST arbitrary JPEG bytes to origin `/run` with `Content-Type:image/jpeg` and optional `X-Request-ID`. The handler checks JPEG headers and a 1 MiB body cap. Native protobuf framing must also fit configured MQ bytes; oversized messages are rejected before native submission because the existing native send path does not propagate queue-send errors reliably. The response carries `request_id,client_request_id,input_sha256,input_bytes,function,submitted_unix_ns,returned_unix_ns,latency_ms,status,native_status,result_base64,error,receiver_before_wait,receiver_after_wait,witness`; valid returned JSON is additionally exposed as `result_json`. `result_base64` is the exact raw result encoded as base64, or JSON null if absent. `native_status` is 3 for EXIT_SUCC and 4 for EXIT_FAIL. Status strings are `success,failure,timeout,submission_error`; HTTP status is 200,503,504,503 respectively. Early validation/availability failures may have a plain-text 4xx/503 response and must still be retained by collectors.
6. Receiver objects contain `to_cloud,receiver_id,node,role,known`. `receiver_id` is the actual native `Routine.Receiver()` value, joined to the retained native lifetime mapping; unknown IDs stay unknown. Before-wait and after-wait observations may differ. Never infer destinations from command-line node labels, container hostnames or output latency.
7. `/state` also exposes `active_http_requests,submitted_requests,completed_requests,unresolved_requests`. These are origin observer counters, not native queue/executor occupancy. HTTP timeout leaves unresolved native work visible; a completion watcher can observe a late result. A timeout before native receive can leave the result permanently unresolved because the existing native wait adapter cancels its wait protocol. Do not label backend idle from HTTP completion alone.
8. `local_processors` is the same-process locked PM observation, independently available on every node: `node,total_cpus,reserved_cpus,committed_cpus,borrowed_cpus,physical_occupied_cpus,observed_unix_ns`. Reserved equals total minus high-priority remaining; committed equals total minus all logical remaining; borrowed equals committed minus reserved. Physical occupied counts native held CPU-set slots, not CPU utilization. Logical grants notified to a waiter may briefly appear committed before physical handoff. This additive read-only getter does not change heartbeat, queues, grants or placement. The parent samples all three node endpoints to include cloud-local borrowing.
9. `/health`, `/config`, `/state` accept GET only. `/config` summarizes frozen campaign settings; `native/<node>/startup.json` stores the full native config, argv and MQ inputs. There is no mutable config or scaling endpoint.

MQ defaults are `--mq-message-bytes=262144 --mq-max-messages=10`; this process sets only its environment variables. The parent launcher must verify the Linux limits permit those values and establish its process RLIMIT_MSGQUEUE. The command changes no sysctls or process rlimits. The original Python PAIX worker used larger default queue sizes, but the campaign worker opens already-created queues and therefore supports the recorded smaller queue capacity. JPEG plus event framing must fit the configured capacity.

CPU numbering follows the native ProcessorManager: resource IDs are host CPU indices 0..N-1. Setting taskset on the gateway does not remap the containers. Audit actual cpusets and coexistence before running. No CPU remapping policy is introduced here. The formal parent launcher uses guest application CPU indices 0–11 and control indices 12–15, preserving the 12+4 budget. These guest indices do not establish physical CPU exclusivity. Node execution/network estimates remain frozen calibration inputs; in particular, a 357 ms origin estimate correctly excludes a local function under the unchanged 350 ms QoS policy.

Ownership and shutdown:

- Every process creates `native/<node>/runtime.lock`, `runtime.jsonl`, `startup.json` and `owned-cgroups.json` inside its chosen campaign root. The log and lock use exclusive creation. Never erase an earlier run to restart; use a new root.
- Native container/cgroup initializers still use the existing containerd `tide` namespace and randomly named `/tide/<ID>` cgroups. A logging hook records only paths whose successful creation is observed in this process. No global cgroup or container traversal/removal is used.
- SIGTERM/SIGINT stops HTTP intake and waits for active callers, then closes this process's manager/stubs/executor pools, closes its PM, stops gRPC, and individually deletes only its recorded cgroup paths. It never calls DeleteAllCgroup/DeleteAllCombCgroup and never removes `/tide` itself. Native entry close may broadcast the normal app-stop event for this campaign app. Stop after retained results and drain observation; shutdown is not a workload deadline mechanism.
- A failed initializer may terminate before normal cleanup. Retain the process log, PID/startup and owned path manifest. Clean only verified owned container IDs/paths after confirming the process has stopped. The hook cannot claim ownership of unrelated or preexisting paths, and this command does not perform emergency global cleanup.
- Native Stub TTL returns permanent processor reservations while keeping per-app pooled containers until app stop. Plot `reserved_cpus`, not reclaimed container count, RSS or utilization. Native borrowed processors also do not change this reservation counter.

Known native dynamic-state hazards reported in discovery remain outside this command: unsynchronized AppState.Stubs reads during add/remove, stale missing GetStub IDs aliasing slot0, and normal transport/queue timeout behavior. Record any failed attempt. The additive `pkg/procmgr/revision_snapshot.go` getter only reads existing fields under the native PM mutex. This adapter does not repair existing shared policy code or change placement.

### Recorded formal source repair

The actual12-application/4-control-CPU preflight exposed the non-RSEP backend's combined-cgroup CPU-vector sizing bug: `runtime.NumCPU()` observes the four-CPU control affinity, while application IDs run0–11. Formal measurements therefore use the exact isolated source snapshot and three-line dimension repair under `results-historical-threefig-20261019/runtime/patches/`, with its before/after hashes and observed-failure regression. The original workspace backend file is deliberately preserved. To reproduce the formal campaign, apply that recorded patch in an isolated source copy before building; use the frozen binary/source/image identities and lifecycle-v3 continuation notes in the campaign. This changes array capacity, not scheduling or resource-allocation policy. The earlier2/4/4 smoke records and failed12CPU preflight remain separate evidence.
