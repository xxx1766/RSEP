# CPU local-capability filtering (C4)

The revised native Tide runtime can require a request to retain a CPU-capable local origin, even when it executes remotely. This implements the CPU projection of the paper's C4 constraint, with the origin fixed as the local component of the assignment.

Use `tide serve --config config.json` with, for example:

```json
{"c4_functions":{"critical_function":true}}
```

The usual configuration defaults still apply. Use the actual submitted function name. The native Go API can also set `Routine.RequireLocalCapacity = true` before source submission. Normal application submission sets `InitSid`; the source binds `LocalNodeID`. Forwarding preserves both fields and the actual resource requirement. The criticality flag does not order execution priorities.

The shared guard in `pkg/c4/check.go` requires a known things/edge origin, positive CPU demand, no GPU demand, and advertised total origin CPU at least equal to that demand. It intentionally does not test free CPU or heartbeat age: this is a structural capability condition, not a liveness or spare-capacity guarantee. Missing metadata fails closed. A busy but capable origin can offload. Destination stub capacity is checked separately before admitting execution.

The guard covers local admission, candidate ranking, expansion, cloud fallback, direct submission helpers, receiving stubs, and the experimental ingress. Rejected requests are retained as terminal failures for the existing wait protocol and do not enter the execution queue. The experimental ingress initializes source metadata when submitting a new request directly.

Use this version on every participating node with consistent function classification. Legacy ordinary messages retain the default resource requirement. Older binaries ignore the new protobuf fields and cannot provide C4 enforcement; this change does not negotiate mixed-version support. Previously collected performance and HTTP fault-adapter results did not enable this filter and are not C4 measurements.

No backup processor is reserved. This does not implement sensing/actuation checks, memory/GPU eligibility, application replica retention, priority queues, automatic retry/migration, or recovery of in-flight remote work. Node advertisements are trusted capability inputs.

## Tests

Run on Linux (the native runtime depends on Linux container/cgroup and POSIX message-queue packages):

```sh
go test -race -count=1 -timeout=60s ./pkg/c4 ./pkg/cmnct ./pkg/routine ./pkg/dev ./pkg/stub/sched ./pkg/stub ./pkg/server/handlers/...
go test -count=1 -timeout=30s ./cmd/tide/... ./pkg/procmgr ./pkg/processor
```

Native stub tests replace only the container executor with a controlled executor. They exercise real admission, dispatch, completion, retained failures, and processor accounting; scheduler transport tests use the communicator's loopback event path. These are runtime correctness tests, not a distributed outage experiment.

## Event schema regeneration

`proto/eventpb/event.codegen.json` is the complete protobuf CodeGeneratorRequest, including dependencies, recovered from the existing generated descriptors and extended with RoutineSubmitEvent fields 6–8. It is the reproducible schema input; no manual edits to generated Go descriptors are needed. Existing field numbers and RPC methods are unchanged.

```sh
go build -o /tmp/tide-protoc-gen-go google.golang.org/protobuf/cmd/protoc-gen-go
go run ./cmd/gen-events /tmp/tide-protoc-gen-go
```

The module pins protoc-gen-go's protobuf dependency to v1.35.2. Only `proto/eventpb/event.pb.go` is regenerated; the service interface is unchanged.
