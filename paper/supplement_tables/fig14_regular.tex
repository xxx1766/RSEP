\section*{Management/runtime footprint at four doubling rates}
The October~27 campaign measured all four Fig.~15 rates together using Ray~2.58.0 and EdgeCore~1.23.1, with archived binaries. The correction below reclassifies the existing 3,410 process snapshots; no experiment is rerun, no request is dropped, and no numerical cells from other dates are substituted. Three randomized blocks contain 36 loaded 30-s cells, nine idle 20-s windows, 40,500 formal requests and 90 separate warmups. The application and deployment configuration is unchanged.

\paragraph{Process accounting.}
CPU deltas and time-weighted PSS use the original arrival-window clipping. Every sampled process belongs to exactly one category: management, runtime support, request-serving path, network/deployment auxiliary, known pre-existing background, or application. The original per-group values are independently reproduced before reclassification. The disjoint categories reproduce every original CPU/PSS total within numerical precision (maximum absolute discrepancy $6.2\times10^{-12}$). All 165 archived raw-file hashes are unchanged; 137 process identities are retained. Components are summed within each measurement block before the three-block mean and $t$(2) interval are computed. Sample intervals are not independent repetitions. Raw intervals are not clipped; only plotted lower error bars are clipped at zero.

\paragraph{Interpretation and unresolved serving behavior.}
The management subtotal retains the complete Tide daemon, including its integrated admission, IPC, HTTP adaptation and request handling; no unmeasured split is inferred. KubeEdge node agents likewise mix management with execution supervision. Thus the main figure cannot establish a pure control-plane or algorithm-only ranking. KubeEdge applications receive direct-Pod HTTP requests after deployment, so increasing offered requests does not imply per-request Pod scheduling. Ray Proxy and Replica belong to its request-serving path and are separately retained, following the component responsibilities in the \href{https://docs.ray.io/en/latest/serve/architecture.html}{Ray Serve architecture documentation}. KubeEdge network/deployment auxiliaries are also separated; the \href{https://kubeedge.io/docs/advanced/cni-edge-networking/}{KubeEdge networking documentation} distinguishes its control tunnel from application traffic.

At 40 requests/s, Ray's original 303.37\% non-application CPU consists of 20.30\% management/runtime and 283.06\% Proxy/Replica. Queue-length-response timeout warnings accompany the increase; its cause remains unresolved. Reclassification changes the reported scope and does not repair the measured service path or prove this is intrinsic Ray overhead. The archived Ray wrapper uses one replica, one ongoing request, an extra loopback HTTP hop, and a new client session per request. At 80 requests/s, valid-return fractions remain 42.44/98.25/22.93\% for Tide/KubeEdge/Ray. Failures remain in the original request records and resource costs. Smaller resident resources do not imply more completed work.

\paragraph{Role definitions.}
\begin{itemize}
\item Tide management: the complete integrated control/adapter daemon. Runtime: the current campaign worker's container shim and the full sampled host containerd. Shared containerd activity is not apportioned or baseline-subtracted, and may include unrelated host work.
\item KubeEdge management: CloudCore, EdgeCore, kube-apiserver, kube-scheduler, kube-controller-manager, etcd and kubelet. Runtime: sampled internal containerd, containerd-shim and pause processes inside the two kind containers (Kubernetes in Docker). Outer host kind shims were not sampled and remain excluded.
\item Ray management: Serve Controller, GCS server and the autoscaler monitor. Runtime: raylet, launcher and remaining agents, including dashboard, logging and runtime-environment support. ProxyActor and ServeReplica are excluded from this subtotal and reported in Table~S33.
\end{itemize}
These role labels are operational process categories, not a claim that every instruction in a listed daemon belongs exclusively to that plane. Management and runtime support are both included in Fig.~15; runtime dependencies have not been silently removed.
