# 三机端侧域断云实验：固定设计

本次“本地”指端侧域 D={A,B}。A（NJ-k2，11.0.4.48）接收并向用户返回所有请求，B（NJ-k3，11.0.4.49）是同域计算节点；C（NJ-k1，11.0.4.47）只承担云端控制，不配置应用执行器。比较 Tide 原生调度、KubeEdge 1.23.1 + EdgeMesh 1.17.0、Ray Serve 2.58.0。使用各自原生路由与扩容，不人为把对照限制为单节点。

## 两组初始状态

- **已有实例分担（warm）**：A、B 各有一个已就绪的应用实例。检验 C 断开后，预先建立的域内执行与返回路径能否持续服务。
- **自主扩展（cold）**：只有 A 存在应用实例；B 的控制组件、资源和镜像已准备，但没有应用实例。检验增压后 B 何时真正启动、何时接收任务、何时向 A 按时返回。联网配对组验证各系统具备真实扩容能力。

Tide 使用现有 Stub/Scheduler/ProcMgr 路径；不更改核心 C4 或冷启动算法。KubeEdge 使用真实 EdgeMesh Service/Endpoint 缓存、官方 CloudStream/EdgeStream 指标链路和标准 CPU HPA（1–2 副本，CPU request 利用率目标 30%）。Ray 的 head/Serve controller 在 C，使用原生 Serve 路由和 1–2 副本自动扩容。其他控制放置方案不属于本次对照范围。

## 相同输入与资源

每个应用节点分配 2 个逻辑 CPU（0–1）、CPU quota 2、512 MiB 内存、swap 0。控制和驱动使用 CPU 8–15。内核为同一 Linux amd64 Go 可执行文件：65,536 字节 × 1,000 次 SHA-256 迭代，GOMAXPROCS=1；每个执行器内部串行执行。资源分配数不等于实际占满两核。

Tide 冷创建可能保留多个空闲预创建进程；它们共享每节点的两核/512 MiB 上限。记录实际进程数，不把预创建进程数等同于独立计算资源。

A、B 硬件异构：30 次独立内核校准的耗时中位数约为 208.97 ms 和 41.57 ms。2 请求/s 低于 A 的单执行器内核参考能力；8 请求/s 高于 A 单执行器参考能力。Ray 与 EdgeMesh 的双端实测在 8 请求/s 下均完成 200/200 次正确、500 ms 内返回。内核参考速率不冒充端到端容量上限。

每轮持续 150 s，共 930 个固定到达时刻：0–30 s 为 2 请求/s；30–60 s 从 2 线性增长至 8 请求/s；60–150 s 保持 8 请求/s。驱动按开环时钟发出每个请求一次，无重试。截止期为从**计划到达时刻**起 500 ms，客户端超时为 2 s；后者不改变截止期定义。固定输入与顺序见 [protocol.json](../protocol/protocol.json)、[order.json](../protocol/order.json)。

## 故障与观测

断云组在计划第 20–110 s，于 C 对 A/B 的自有实验 TCP 端口设置 DROP，包含已有 TCP 连接，以及 C 的 INPUT/OUTPUT/FORWARD 路径；A–B 通信保留。SSH 不在实验端口范围。保留每条规则、实际安装/撤销时间、命中计数及精确清理回执，并设置独立有界撤销保险。

A 每秒探测 B 和 C。A–B 必须可达，稳定断云窗口内 A–C 必须不可达；联网配对轮全程可达。A 在每轮前后分别对 B、C 采集 20 次时钟括号，保存最小 RTT 估计，并检查漂移与不确定性。

每个请求保留正确返回、有效但超时返回、HTTP 错误、连接失败、客户端超时和缺失记录。成功需校验请求 ID、独立 Python SHA 校验值及处理字节数。执行位置由**物理机器上采集的进程/执行器与请求日志**关联；不依赖返回中的 node 标签。B 的启动、传输就绪和首个按时返回分别记录。

## 分析单位

三系统 × 两初始状态 × 联网/断云 × 三次重复 = 36 轮。按重复分块随机排列配对及配对内顺序，运行前冻结。失败请求保留在分母，失败轮次不按结果重跑。推断单位是轮次/配对，非同一轮中的大量相关请求。三次重复报告均值及 t(2) 95% 区间，并保留每轮值。

主指标 R_srv 为稳定断云窗口**到达队列**中，A 在 500 ms 内收到正确结果的比例；所有提供请求均入分母。本实验权重均为 1。另报按实际返回时刻计算的 A/B 有效吞吐量、延迟、错误及 B 就绪时间；转换期与跨期返回单列。联网组使用对应计划窗口。

R_cap 是域内结构能力满足率，不能替代 R_srv。关于公式域边界、单机任务不能跨机加 CPU、现有 C4 仍检查起点 A 的 CPU、以及固定 R_cap 在目标函数中为常数的问题，见 [formula-assessment.md](formula-assessment.md)。

正式结果须同时通过独立协议审计与独立结果重算。预实验数据仅用于校准和路径验证，不混入 36 轮统计。

## 测量开始前的基础设施修订

首次正式部署尝试 `f1-ray-cold-online` 在驱动启动前失败，提供请求数为 0。日志定位到 C 的自有 KubeEdge 转发进程使用临时源端口 34026，阻止 Ray dashboard agent 绑定其固定端口。保留该次尝试及第一版冻结文件；这次部署错误不作为断网服务结果。

第二版冻结前，在三台主机及三个自有 KubeEdge 网络命名空间中，合并保留 34000–34299 和 34443，防止内核将服务端口用于临时出站连接。保留原值、网络命名空间标识和恢复租约；重连占用端口的自有云转发进程。Ray 清理改用 PID、启动时间、执行文件、UID 和 cgroup 见证，支持运行时进程标题变化。调度、路由、扩容参数及应用资源预算均不变。第二版继续原随机顺序，仅为首次失败且无提供请求的条件使用新尝试 ID，并明确保留被替代的部署尝试。
